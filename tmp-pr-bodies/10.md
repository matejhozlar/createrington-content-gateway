Nothing deploys the gateway yet: a release merge into `main` is only a merge. This adds the deploy workflow for Createrington's box, where the gateway runs as a host process under systemd, and the few repository pieces it needs.

- **`.gitea/workflows/deploy.yml`** runs on the merge of a release PR into `main` (and by hand on `main`). It checks out `main`, builds the static binary on the box's Docker with the Dockerfile's new `binary` stage (`--target binary --output type=local`, so the build path is the same one the image uses and its BuildKit cache is kept), exports the Infisical `prod` environment to `.env`, installs the binary next to the previous one (`content-gateway.previous`, so a rollback is a rename and a restart), touches `.restart-trigger` for the systemd path unit, and waits until `/v1/healthz` reports the deployed commit. The health check runs in a `--network host` curl container because a job container's loopback is not the host's. Docker is used for the build and that check only: the gateway itself is not a container.
- The deploy directory and the Infisical project come from the `DEPLOY_DIR` and `INFISICAL_PROJECT_ID` repository variables (both set), the Infisical credentials from secrets, so no box-specific path or id is tracked. Files the job writes are chowned to the directory's owner, which is the service user.
- **`Dockerfile`**: a `binary` stage (`FROM scratch`) holding only the binary; the default image stage is unchanged.
- **`.dockerignore`** leaves the client package, its `node_modules` and the scripts out of the build context, which only needs the crates.
- **README**: how to run the binary as a host process and what the workflow does.

The box side (systemd units, the gateway's own Redis container, the runner mount of `/opt/content-gateway`) is in the infrastructure repository.
